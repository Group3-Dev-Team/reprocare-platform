# Deployment configuration

The canonical project is [Group3-Dev-Team/reprocare-new](https://github.com/Group3-Dev-Team/reprocare-new).

- **FastAPI service** uses `DATABASE_URL` for PostgreSQL, `APP_ENV=production`, `ALLOW_DEMO_ACCOUNTS=false`, and `CORS_ORIGINS` set to the exact HTTPS frontend origin or comma-separated origins. Store the database URI, optional bot HTTP `IMPORT_API_KEY`, and optional `GOOGLE_PLACES_API_KEY` in the host’s private environment or secret store. `SESSION_DAYS` controls token lifetime. Supabase can provide PostgreSQL while ReproCare handles application authentication.
- **React build** uses `VITE_API_URL` set to the public HTTPS FastAPI origin, without `/api` at the end. Keep `VITE_DEMO_MODE=false` for the connected application. Serve the build’s `dist/` directory and configure the static host to serve `index.html` for client-side routes. The Leaflet directory map uses OpenStreetMap tiles. An optional `VITE_GOOGLE_MAPS_BROWSER_KEY` is visible in the browser and should be restricted by HTTP referrer and API.
- **Private bot runner** uses the database URI for direct imports or a server-side `IMPORT_API_KEY` for authenticated HTTP imports. `GOOGLE_PLACES_API_KEY` enables Places lookup, and `APIFY_API_TOKEN` enables TikTok collection. Facebook uses a Playwright browser profile with a manually signed-in session. Keep `REPROCARE_BOT_HOME`, browser profiles, staged feedback and caches outside the Git checkout. The bot can run independently of the web services.
- **Database releases** should use a private backup and a rehearsal on a separate database before applying reviewed additive migrations. For an already configured database, verify schema and connectivity first. The application retains collected feedback, and Facebook data remains subject to the review queue. Do not run test resets, fixture seeds or purge commands against the application database.
- **Migrations** in `backend/migrations/versions/` are additive and applied in name order by `python -m app.database.migrate`:
  `0001`–`0003` (public feedback tables and Facebook moderation), `0004` (password recovery), `0005` (Google sign-in) and `0006` (one pending appointment request per patient, facility and date). Before `0006`, check for existing duplicate pending requests with the query in the migration file. Fresh databases created by `init_db` already include the index.
- **Optional integrations** stay disabled until configured: password recovery (`PASSWORD_RESET_*` SMTP settings, migration `0004`), Google sign-in (`GOOGLE_OAUTH_*`, migration `0005`), facility photo uploads (`CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, `CLOUDINARY_API_SECRET`; the backend signs each upload and the secret never reaches the browser) and the WhatsApp support link (`VITE_WHATSAPP_SUPPORT_NUMBER`, only with an approved public number). Displaying uploaded photos on listings additionally needs a stored photo field, which is not part of the current schema.
- **Search indexing**: set `VITE_PUBLIC_SITE_URL` to the public HTTPS origin at build time to emit an indexable `robots.txt` and `sitemap.xml`. Without it the build disallows all crawling. Dashboards, authentication callbacks, password reset and API paths are always excluded.
- Keep `backend/.env` and any frontend local overrides private. The checked-in examples contain names and placeholders. Run backend and browser-bot tests using dedicated disposable PostgreSQL databases.
